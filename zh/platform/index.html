一个下午即可上线

首次四步，之后就只是发送。

  1. 接入你已在付费的服务商

    打开控制台，选择服务商，把其后台的凭证粘贴进来。不做任何迁移：号码、短码与发送方 ID 仍注册在原处，服务商也继续直接向你计费。

  2. 发出第一条消息

    可以在控制台里填写，也可以通过 API 从自己的后端发送。验证码流量与营销流量的标注方式，与你在自己代码里的标注一致。

  3. 看清究竟发生了什么

    日志为每条消息保留服务商响应、归一化错误码以及之后的投递回执。下次有人说「没收到」，按收件人一查便知。

  4. 需要余量时再加一个账号

    第二个连接抬高上限，并在第一个停止接收流量时顶上。按优先级排序、在各自内部给发送号码配权重，两者都会写入同一份日志。

短信渠道上你能得到什么

6 家短信服务商可自助接入 —— 33 —— 每一家实际需要的凭据字段都列在自己的页面上。其下是一套包含 个适配器的短信适配库，按需开放。在它们之上还有：

路由与故障转移

把多家服务商与发送号码绑定到一条路由，各自带优先级和权重。主服务商拒收时由下一位接手——某家服务商状态不好，只会降级为发送变慢，而不是彻底静默。

按真实配额限速

每个连接都带有你设置的发送速率，我们按它排队，而不是以服务商能接受的最快速度猛发。正是这个排队，让账号从一开始就不至于被限流。

送达回执，已聚合

服务商回调被汇总并归一化为每条消息一个状态，原始服务商代码一并保留——于是回答「到底送到了吗」不再需要对齐五种 webhook 结构。

退订抑制

回复 STOP 会写入抑制记录，每次营销发送前都会检查，因此已退订的人不再收到营销消息。营销流量默认采用「失败即关闭」策略。

编码与分段计费

GSM-7 还是 UCS-2，决定一条消息会拆成几个计费分段。编码按连接设置，分段数留在记录上，因此服务商账单可以逐行对账。

一套统一的错误语义

每家服务商上报失败的方式都不同。我们把它们归一化，并把原始码一并保留，因此同一个失败无论来自哪个账号，读起来都一样。

产品问题

我的一家服务商宕机会怎样？
在短信通道上，一次拒收并不等于消息终结：路由按优先级排序并在连接内加权，某家服务商状态不好只会降级为发送变慢，而不是彻底静默。有个限制值得知道：故障转移只在你已接入的账号之间搬流量，绕不开与目的地本身绑定的拒收。
需要新号码或新的发送方 ID 吗？
不用。你接入的是已有账号，已注册的号码、短码与发送方 ID 原样保留，收件人看到的仍是同一个发送方。不做携号转入，也不重新注册。
我还能继续从自己的后端发送吗？
可以。既可以在控制台发送，也可以通过 API 发送。发送 API 按通道分别编写文档，而不是做成统一接口，因为各通道支持的能力并不相同——文档里逐通道写明了差异。
服务商对我的流量限流时会怎样？
每个连接都带有你设置的发送速率，平台按它排队，而不是以服务商能接受的最快速度猛发。限流会作为限速信号返回，而不是一次发送失败——这正是「慢一分钟」和「丢一条消息」的区别。
停止使用后，我的配置会怎样？
没有什么需要拆解。账号、发送方身份与服务商关系自始至终都是你的，平台自己也没有服务商账号——吊销你签发的凭证，发送就回到起点。
如何开始？
接入一个你已有的服务商账号，然后从控制台发送。套餐限制的是连接数而不是消息数，所以先用一个连接验证整条链路，再决定档位就够了。
